## 1. 지켜야 할 제약 (어기면 그 자체가 결함이다)

개인용 Android 앱. Kotlin + Compose + Hilt + Room + Firestore.

- **Room이 Single Source of Truth.** UI는 Room Flow만 구독한다. UI가 Firestore를 직접 구독하면 아키텍처 위반
- **Offline-First.** 일반 push(`Repository.syncSafe`)는 `@ApplicationScope`에서 fire-and-forget이며 **오프라인에서도 호출부를 막지 않아야 한다.** 과거에 오프라인 hang으로 실제 장애가 났고 그걸 고친 구조다
- 삭제는 전부 tombstone(`deletedAt`). pull은 upsert-only라 hard delete하면 다음 로컬 변경 때 행이 부활한다
- `collectAsStateWithLifecycle` 금지, `collectAsState()`만. ViewModel은 `@HiltViewModel` + `@Inject constructor`
- 새 DAO/Repository는 `di/AppModule.kt`에 `@Provides` 등록 필수. 이 프로젝트의 Repository는 `@Provides`가 생성자 인자를 하나씩 넘기는 방식이라 인자 추가 시 여기도 고쳐야 한다
- 커밋 메시지는 conventional commits. **`Co-Authored-By` 줄을 절대 넣지 마라**

**건드리지 말 것 (검증에서 타당함이 확인된 설계):**

- `syncSafe`가 5벌 사본으로 존재하는 것 — 4개는 fire-and-forget, `SyncRepository`만 suspend다. 통합하면 오프라인 hang 회귀
- **재시도 경로(`retryFailed`)가 `SyncLogger`를 호출하지 않는 것** — 호출하면 `recordFailure → 워커 예약 → 재시도 → 실패 → recordFailure` 무한 순환
- `SyncLogger`가 `AuthRepository`를 주입받지 않는 것 — Hilt 순환(`AuthRepository → SyncRepository → SyncLogger → AuthRepository`)
- LWW 머지의 단일 출처인 `mergeEvents`/`mergeTodos`/`mergeFinance`/`mergeBudgets` 4개 함수 — 사본을 다시 만들지 마라
- 게이트 분모에서 pull을 제외하는 정책
- 기존 집계 사본 3곳(`HomeViewModel`·`FinanceDashboardViewModel`·`LSyncWidget`)과 `data/report/MonthlyAggregate.kt` 단일 출처 규칙

## 2. P0 — 재전송이 다른 기기의 최신 변경을 덮어씀

### 확인된 사실

`FirestoreDataSource.kt:25`(및 `upsertTodo`/`upsertFinance`/`upsertBudget`)는

```kotlin
events().document(entity.id).set(entity.toMap(), SetOptions.merge()).await()
```

**조건 없는 쓰기**다. `SetOptions.merge()`는 "맵에 없는 필드를 보존"할 뿐, 맵에 있는 필드는 원격이 더 최신이어도 덮어쓴다. `toMap()`에는 `updatedAt`도 포함된다.

`SyncRepository.retryFailed` → `resend()`(`SyncRepository.kt:120-136`)는 이 메서드로 **Room의 오래된 행을 무조건 전송한다.**

**피해 경로:** 앱에서 push 실패 → 웹(또는 다른 기기)에서 같은 문서를 더 최근에 수정 → 앱이 재전송 → 웹 변경이 사라지고 원격 `updatedAt`이 과거로 되돌아가 **이후 pull로도 복구되지 않는다.** 이 프로젝트는 실제로 웹 클라이언트(`web/`)를 함께 쓴다.

기존 TechSpec §12.3의 *"`updatedAt`을 새로 찍지 않으므로 LWW 기준이 보존된다"*는 **틀린 서술이다.** LWW는 pull 시점의 클라이언트 측 비교로만 강제되고 쓰기 경로에는 아무 조건이 없다. 이 문장도 함께 고쳐야 한다.

### 요구 계약

**재전송 전용 조건부 쓰기 경로**를 만든다.

1. 원격 문서가 **없으면** 생성한다(최초 push가 실패한 경우가 이것이다)
2. 원격 문서가 있고 `remote.updatedAt > local.updatedAt`이면 **쓰지 않고 건너뛴다**
3. **비교와 쓰기는 같은 Firestore 트랜잭션 안에서** 수행한다. 읽고 나서 쓰기 전에 다른 클라이언트가 끼어들 수 있다
4. `todos` 재전송은 연결된 Finance까지 **한 트랜잭션**으로 처리한다(읽기 2회 → 쓰기 최대 2회)
5. 건너뛴 경우(원격이 더 최신)는 **실패가 아니다.** 해당 로그를 해소 처리하고, Room은 다음 pull에서 원격 최신값을 받는다

### 연결된 두 문서 중 하나만 원격이 더 최신일 때 (지시 수정 2차)

1차 지시서의 2번(문서 단위 건너뛰기)과 4번(쌍 단위 원자성)이 이 경우에 충돌했다. **판정 단위를 문서로 확정한다.**

```
예) Room:  Todo updatedAt=200,  Finance updatedAt=100
    원격:  Todo updatedAt=150,  Finance updatedAt=300
    → Todo는 쓴다(200 > 150), Finance는 건너뛴다(300 > 100)
```

- **두 문서를 각각 독립적으로 판정하되, 두 판정과 두 쓰기를 같은 트랜잭션 안에서** 수행한다. "둘 다 쓰거나 둘 다 안 쓰거나"로 묶지 마라
- **묶으면 안 되는 이유:** 한쪽이 최신이라고 둘 다 건너뛰면 위 예의 Todo 로컬 변경(200)이 영영 전송되지 않는다. 원격 Todo는 150에 머무르고, 다음 pull에서도 `150 > 200`이 거짓이라 머지되지 않아 **로컬과 원격이 조용히 갈라진 채 고착된다**
- **관계가 깨지는 유일한 경우는 dangling reference** — Todo가 가리키는 Finance 문서가 원격에 아예 없는 상태. 이건 계약 1번(원격 문서가 없으면 생성)이 이미 막는다. 건너뛰기는 원격 문서가 **존재하고 더 최신일 때만** 일어나므로 참조 대상은 항상 존재한다
- 로그는 **두 문서 모두가 "썼음" 또는 "원격이 더 최신이라 건너뜀"으로 끝났을 때** 해소한다. 예외로 중단된 쪽이 하나라도 있으면 실패로 센다

### 남는 한계 (수용하기로 한 것 — 더 고치지 마라)

문서 단위 LWW라서 **교차 문서 불변식은 보장되지 않는다.** 위 예에서 로컬이 Todo를 미완료로 되돌렸고(200) 웹이 같은 Finance의 금액을 고쳤다면(300), 원격은 "미완료 Todo + 제외되지 않은 Finance"라는 의미상 어긋난 쌍이 될 수 있다.

**이건 재전송이 만드는 문제가 아니다.** 웹이 그 Finance를 더 최신으로 고친 이상, 다음 pull에서 **로컬도 똑같은 조합**이 된다(원격 300 > 로컬 100이라 Room이 덮어쓰인다). 문서 단위 LWW를 쓰는 한 재전송 경로에서만 다르게 처리할 근거가 없고, 교차 문서 불변식을 강제하려면 별도의 충돌 해소 설계가 필요하다 — **이 phase의 범위가 아니다.** §7에 따라 이 한계를 TechSpec에 기록만 한다.

### 반드시 지킬 것

- **일반 push 경로(`Repository.syncSafe` → `upsertX`)를 트랜잭션으로 바꾸지 마라.** Firestore 트랜잭션은 **오프라인에서 동작하지 않는다**(`set()`은 로컬 큐에 쌓였다가 나중에 전송되지만 `runTransaction`은 연결이 없으면 실패한다). 일반 push를 트랜잭션화하면 Offline-First가 깨진다. 재전송 워커는 `NetworkType.CONNECTED` 제약 아래 돌므로 트랜잭션을 써도 된다
- **Firestore 트랜잭션은 모든 읽기를 모든 쓰기보다 먼저** 해야 한다. Todo+Finance를 함께 쓸 때 읽기 2회 → 쓰기 2회 순서를 지켜라. 어기면 런타임 `IllegalStateException`
- 트랜잭션 람다는 **재실행될 수 있다.** 그 안에서 Room을 건드리거나 부수 효과를 내지 마라. Room 조회는 트랜잭션 바깥에서 끝내고 값만 넘긴다

- 스키마 변경은 필요 없다. `WHERE` 절만 고치면 된다 — **AppDatabase 버전을 올리지 마라**

## 4. P1 — 실행 중인 워커가 새 실패를 놓침

### 확인된 사실

`SyncRetryTrigger.kt:31`이 `ExistingWorkPolicy.KEEP`을 쓴다. 워커가 실행 중일 때 들어온 예약은 버려지고, 워커는 이미 읽은 목록만 처리한 뒤 `Result.success()`로 끝난다.

**정확한 범위:** 워커 종료 후 실패가 한 번이라도 더 기록되면 그때 정상 예약된다. 갇히는 것은 "실행 중에 들어온 실패가 그 뒤로 마지막인" 경우다. 좁아 보이지만 **네트워크가 끊겼다 붙는 순간이 정확히 그 상황**이라 실제로 발생한다.

### 지시 수정 (2차) — 종료 직전 재조회만으로는 부족하다

1차 지시서는 "`doWork()` 끝에서 재조회 → 남아 있으면 `Result.retry()`"만 요구했는데, **그것으로는 수락 조건을 만족하지 못한다는 지적이 맞다.** 아래 순서가 여전히 가능하다:

```
[워커] 재전송 완료 → 마지막 재조회 = 0건
[앱]                    ↓ 이 사이에 새 실패 기록
[앱]                    recordFailure → schedule()
[WM]                    KEEP → 워커가 아직 RUNNING → 예약 버려짐
[워커] Result.success() 반환 → 대기 중인 예약 없음
```

`KEEP`은 같은 이름의 작업이 **RUNNING일 때도** 새 예약을 버린다. 그리고 워커 **내부**에서 몇 번을 재확인하든 그 확인 뒤에 창이 다시 생기므로, 워커 안의 점검만으로는 원리적으로 닫을 수 없다.

### 요구 계약 (확정)

**경쟁 조건을 없애는 대신 유실을 회수하는 쪽으로 간다.** 이 프로젝트가 이미 쓰는 패턴이다 — 정기 리마인더는 알람 유실에 대비해 *발화 시 재무장 + 앱 시작 `syncAll()` + 재부팅/업데이트 워커*로 3중화돼 있다(`LSyncApplication.onCreate()`, `AlarmRestoreWorker`).

1. `doWork()` 종료 직전에 미해결 실패를 **다시 확인**하고, 남아 있으면 `Result.retry()`를 반환한다 (흔한 경우를 여기서 잡는다)
2. **`ExistingWorkPolicy.KEEP`을 유지한다.** 백오프 보호를 위해 `REPLACE`로 바꾸지 마라 — 실패가 연달아 기록될 때마다 실행 중인 워커를 죽이고 백오프를 초기화한다
3. **앱 시작 안전망을 추가한다.** `LSyncApplication.onCreate()`에서 `SyncRetryTrigger.schedule()`을 1회 호출해, 위 창에서 버려진 예약을 다음 앱 실행에 회수한다. `reminderScheduler.syncAll()` 호출부 근처에 같은 결로 넣으면 된다
   - 미해결이 0건이면 워커는 즉시 `Result.success()`로 끝나므로 빈 실행 비용은 무시할 수 있다
   - 미로그인 상태에서도 워커가 `Result.success()`를 반환하므로 안전하다
4. **영구 실패에서 무한 재시도가 되지 않게 상한을 둔다.** 권한 오류처럼 재시도로 절대 풀리지 않는 실패가 있으면 배터리만 태운다. `runAttemptCount`로 상한을 정하고 초과 시 `Result.success()`로 종료한다(기록은 남아 있으므로 사용자가 화면에서 수동 재시도할 수 있다). 상한 값은 재량이되 근거를 보고에 적어라

### 남는 한계 (수용하기로 한 것 — 더 고치지 마라)

위 창 자체는 닫히지 않는다. 최악의 경우 "그 창에서 기록된 실패가 다음 앱 실행까지 자동 재시도되지 않음"이다. 화면의 "지금 재시도" 버튼이 수동 경로로 남아 있고, 그 뒤 실패가 한 번만 더 기록돼도 정상 예약된다.

`APPEND_OR_REPLACE`로 창을 실제로 닫는 선택지도 검토했으나 채택하지 않았다 — 연속 실패 시 실행이 줄줄이 쌓이고(대부분 빈 작업), 현재 작업이 `retry()` 백오프에 들어갔을 때의 체인 동작을 새로 검증해야 한다. 개인용 앱에 수동 재시도 경로까지 있는 상황에서 비용이 이득보다 크다고 판단했다.

**이 한계는 §7에 따라 TechSpec에 명시적으로 기록한다.** 알고 수용한 것과 모르고 빠뜨린 것은 다르다.

## 5. P1 — 원본 행이 없어도 재전송 성공으로 표시

### 확인된 사실

`SyncRepository.kt:120-136` `resend()`는 `getById()`가 `null`이거나 `target`이 알 수 없는 값이면 **조용히 정상 반환**하고, 호출부(`SyncRepository.kt:109-114`)가 `markResolved`한다.

이 동작 자체는 "되살릴 원본이 없는 경고가 영구 잔류하지 않게" 의도적으로 넣은 것이다. 문제는 아래 조합이다:

- `AuthRepository.signOut()`(`AuthRepository.kt:55-60`)은 `clearLocalUserData()`로 동기화 5테이블을 비운다
- 그런데 **`sync_log`는 의도적으로 보존한다**(로컬 전용 진단 데이터라 `reading_plan`·`memos`와 같은 취급)
- 재로그인 후 pull이 끝나기 전에 워커가 돌면 `getById()`가 전부 `null` → **미해결 실패 전체가 "해소됨"으로 표시된다.** 원격에 올라간 적이 없는데도

데이터 손실 자체는 로그아웃 시점에 이미 발생한 기존 구멍이다. 이번 수정의 목표는 **그 사실을 사용자에게 숨기지 않는 것**이다.

### 요구 계약

- **원본 부재를 원격 전송 성공과 구분한다.** 최소한 `RetryResult`에서 구분 가능해야 한다
- **은폐보다 잔류가 낫다.** 원본이 없는 로그를 성공으로 표시하지 마라. 다만 영구히 "실패"로만 남겨 사용자가 손쓸 수 없게 두는 것도 피한다 — 화면에 `원본 없음`처럼 **상태가 드러나게** 하거나, 해소 조건을 명시적으로 정의한다(예: 해당 사용자에 대해 pull이 한 번 성공한 뒤에도 원본이 없으면 그때 해소)
- 알 수 없는 `target`과 `entityId == null`도 조용히 해소하지 마라
- 어떤 정책을 택했든 **그 이유를 코드 주석과 보고서에 남겨라**

## 6. P2 — 에러율 단위 설명이 실제 분모와 다름 (문서 수정)

### 확인된 사실

`FinanceRepository.kt:138-152`는 정산 그룹 리더를 삭제할 때 그룹 구성원마다 `syncSafe`를 호출한다. **사용자 작업 1회가 로그 N+1행**이 된다.

`docs/PRD.md` 2.9의 *"사용자 액션 1회(원격 연산 1회) = 1건으로 센다"*는 괄호 안 두 단위가 같다고 전제하는데 여기서는 다르다. `docs/TechSpec.md` §12.1의 "원격 연산 1회 = 로그 1행"은 정확하다.

### 요구 계약

- **집계 단위는 "원격 연산 수"로 유지하고 문서 서술만 정정한다.** 정산 그룹 로깅을 하나로 묶는 리팩토링은 하지 마라 — 검증된 삭제 로직을 건드릴 위험이 이득보다 크다
- `docs/PRD.md` 2.9와 `docs/TechSpec.md` §12.6의 단위 설명을 일치시킨다. 화면 문구(`내 작업 실패 N / 시도 M`)도 오해를 주면 함께 고친다

## 7. 문서 동기화 (수정과 같은 커밋에)

- `docs/TechSpec.md` §12.3의 **"`updatedAt`을 새로 찍지 않으므로 LWW 기준이 보존된다"를 삭제하고** 조건부 쓰기 계약으로 대체한다. 이 문장은 틀렸고, 틀린 근거가 문서에 남아 있으면 다음 작업자가 같은 실수를 반복한다
- 가지치기 규칙, 워커 재예약·상한, 원본 부재 정책을 §12.2~§12.4에 반영
- **워커 재예약의 남는 경쟁 조건을 명시적으로 적는다** — `KEEP`이 RUNNING 중 예약을 버리므로 "마지막 재조회 이후 ~ 종료 사이"에 기록된 실패는 다음 앱 실행의 안전망 트리거로 회수된다는 것, 그리고 `APPEND_OR_REPLACE`를 검토했으나 채택하지 않은 이유. 수용한 한계를 문서에 남겨야 다음 작업자가 "빠뜨린 것"으로 오해하지 않는다
- TechSpec 버전을 v0.14 → **v0.15**로 올린다
- `docs/PRD.md` 2.9에 P0에서 얻은 정책을 한 줄 추가한다: 재전송은 원격이 더 최신이면 쓰지 않는다
